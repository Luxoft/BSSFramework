# Architecture

BSS Framework is a set of NuGet packages (`Luxoft.<ProjectName>`) for building business applications on .NET 10. An application describes the **domain model** and **metadata** (attributes, security rules, subscriptions). Everything else — the BLL layer, DTOs, ORM mapping, WebApi controllers, the DB schema — is generated by the framework or provided ready-made (see [codegeneration.md](codegeneration.md)).

Two ORMs are supported: **NHibernate** and **Entity Framework**. The same domain model and the same set of integration tests work on both.

## External dependencies of the framework

Part of the functionality lives in separate packages that are not in this repository:

| Packages | What they provide |
|---|---|
| `Anch.*` (version in `Directory.Packages.props`, property `Anch`) | Core (`Anch.Core`), the **security system** (`Anch.SecuritySystem*`: roles, contexts, permissions, virtual permissions, role-based notifications), `GenericQueryable`, `GenericRepository`, `OData`, `HierarchicalExpand`, DB testing infrastructure (`Anch.Testing.*`) |
| `Luxoft.Bss.Platform.*` | Logging, API documentation, middleware, integration events |
| Hangfire, FluentMigrator, FluentNHibernate, NHibernate.Envers, EF Core, MediatR, FluentValidation | Background jobs, migrations, ORM, audit, other |

Therefore the description of Role&Context security in this repository is limited to wiring and configuration (see [security.md](subsystems/security.md)). For the internals of `Anch.SecuritySystem`, see the documentation of that package.

## Layers and folders

Code in `src/` is grouped **by domain**. Within a domain a uniform split is used:

```
*.Abstractions   contracts (interfaces, attributes)
*.Domain         models and DTOs of the subsystem itself
*.Runtime        implementation
*.Tests          tests
```

Extensions are wired through DI: contracts are in `*.Abstractions`, implementations in `*.Runtime`, registration in `ServiceCollectionExtensions` / `Framework.DependencyInjection`.

| Folder | Purpose |
|---|---|
| `Framework.Core` | Layer 0: extensions, reflection, expressions (`Expression`), Maybe / TryResult, Period / Range, serialization. Depends on nothing |
| `Framework.DependencyInjection` | Service registration helpers |
| `Framework.ExpressionParsers` | Expression parsers (C# and "native") |
| `Domain` (`Framework.Relations`, `Framework.Restriction`) | Attributes and metadata of the domain model: `IMaster` / `IDetail`, `[UniqueGroup]`, `[Required]`, `[MaxLength]` |
| `Validation` | Validators and validation attributes (see [validation.md](subsystems/validation.md)) |
| `Database` | DB abstractions; `*.NHibernate`, `*.EntityFramework`; audit (`EnversAudit`, `InlineAudit`); `Tracking`; `DBGenerator`, `DALGenerator`; `SqlMapper`. `*.Legacy` sub-projects are the old API (see [legacy.md](legacy.md)) |
| `BLL` | Business logic layer: `BLL.Abstractions/Domain/Runtime/Events/Validation`, `BLL.DTOMapping` |
| `Application` | Application layer: repositories, `IServiceEvaluator`, jobs, named locks, events |
| `Infrastructure` | Hangfire, Swagger, DI composition (`AddBssFramework`), middleware, DAL listeners |
| `Notification`, `Subscriptions` | Sending notifications and subscriptions to object changes (see [notification.md](subsystems/notification.md)) |
| `Projection`, `ExtendedMetadata` | Projections of domain objects and extended metadata attributes |
| `Configurator` | Configurator (`ApplicationVariable`, events) |
| `AutomationCore` | Integration-test infrastructure (see [integrationtests.md](integrationtests.md)) |
| `CodeGeneration` | Code generators: `CodeDom`, `FileGeneration`, `DTOGenerator*`, `BLLGenerator`, `BLLCoreGenerator`, `ServiceModelGenerator`, `WebApiGenerator`, `ProjectionGenerator` |
| `_Authorization`, `_Configuration` | Ready-made authorization and configuration subsystems: domain, BLL, generated DAL / DTO, WebApi |
| `_SampleSystem` | Reference application and all integration tests |

The `_` prefix means "an application system built on the framework". These systems are also consumers of code generation.

## Anatomy of an application on the framework

A typical project chain, using `SampleSystem` as an example:

```
SampleSystem.Domain                      domain entities + attributes
        │
        ├─ SampleSystem.Domain.Projections / .ManualProjections / .LegacyProjections
        │
SampleSystem.Generated.DAL.{NHibernate|EntityFramework}   ORM mapping (generated)
SampleSystem.BLL.Core / SampleSystem.BLL                  business logic (generated + hand-written code)
SampleSystem.Generated.DTO                                DTOs and mapping services (generated)
SampleSystem.Security(.Abstract)                          roles, contexts, security rules
SampleSystem.Validation                                   validation rules
SampleSystem.EventMetadata / .Events                      event metadata
SampleSystem.Subscriptions.Metadata                       notification subscriptions
SampleSystem.WebApiCore                                   controllers (generated) + GenericProgram
SampleSystem.ServiceEnvironment                           shared DI composition
SampleSystem.ServiceEnvironment.{NHibernate|EntityFramework}   ORM selection
SampleSystem.WebApiCore.{NHibernate|EntityFramework}      executable host (Program.cs)
```

### ORM selection

ORM-specific parts are reduced to two `IBssFrameworkExtension` implementations; the rest of the application does not depend on the ORM:

- `SampleSystemEntityFrameworkExtension` registers `SampleSystemDbContext` (and a separate `SampleSystemEnversAuditDbContext` for audit), enables `UseGenericQueryable`, lazy proxies, Envers and Inline audit;
- the NHibernate counterpart lives in `SampleSystem.ServiceEnvironment.NHibernate`.

The host (`SampleSystem.WebApiCore.EntityFramework/Program.cs`) passes the required extension to `GenericProgram.Main(args, extension)`.

### DI composition

All configuration is assembled in `AddGeneralDependencyInjection` (`SampleSystem.ServiceEnvironment/DependencyInjection/`). It calls `AddBssFramework` and chains in:

- the security system (`AddSecuritySystem`: contexts, roles, rules, user source, virtual permissions);
- named locks (`AddNamedLocks`);
- domain event metadata (`SetDomainObjectEventMetadata`) and DAL listeners (`AddListener<…>`);
- subscriptions and notifications (`AddSubscriptions`, `AddLegacyNotification`);
- the BLL context (`AddBLLSystem<ISampleSystemBLLContext, SampleSystemBLLContext>`);
- DTO mapping (`SetDTOMapping`);
- application services (`AddGeneralApplicationServices`).

Blocks marked with the `// Legacy` comment in code belong to the old API (see [legacy.md](legacy.md)).

The host calls `AddGeneralDependencyInjection` once. Tests do the same: this verifies exactly the composition that runs in production.

### Request flow

1. The request arrives at a generated controller (`Controllers/_Generated`). Routes: `Main`, `MainQuery` (`mainQueryApi/…`), `Integration` (`integrationApi/…`), `Audit` (`mainAuditApi/…`), `Auth` (`authApi/…`), `Config` (`configApi/…`).
2. The controller executes the method through `IServiceEvaluator` within a DB session and transaction (`DBSessionEvaluator`).
3. The BLL applies security rules (`ISecurityContext`, roles and operations, query filtering) and validation, and calls the DAL.
4. DAL listeners (`IDALListener`) react to changes: audit, events, subscriptions.
5. The result is converted to DTOs by the mapping service (`ISampleSystemDTOMappingService`).

## Principles

- **The model comes first.** A new entity is described once in `Domain`; the DAL, DTOs, BLL and controllers appear after generation.
- **Generated code is not edited by hand.** Change the generator or the model, then regenerate. CI checks that it is up to date (`CheckGenTests`).
- **The ORM is replaceable.** Application code must not depend on EF or NHibernate directly.
- **Extension through DI.** New behavior is wired by registration in `IBssFrameworkSetup`, not by inheriting internal classes.
- **Nullable is enabled everywhere**, zero warnings (see [CONTRIBUTING.md](../CONTRIBUTING.md)).
